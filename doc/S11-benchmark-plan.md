# S11 三十组双分支样例与基线协议

依据设计 5B.3、实施方案 S11-T01–T03；延续[合并实施计划](S11-merge-plan.md)。本文件先固定输入及判定，不把规格、准备运行或内核向量当成正式三十组结果。每例应有独立项目、真实来源 Run、base、两个实际分支 HEAD、原始 CAS 和三方来源；未知字段必须拒绝，不能扩展为自然语言或单位自动转换。预期由现有设计规则推导，独立人工复核状态单列，不能把自动断言称为人工审阅。

## 样例与预期

固定 30 例、三类各 10 例，无开发/保留划分，不根据首轮成绩替换失败例。序号和场景由 `tests/fixtures/merge/v1/cases.json` 固定。

补读/保存、计划和配置变化通过明确 LiveOverrides 与真实 Runtime 产生；错误报告通过显式产物补丁进入新 Live 分支，失败来源仍保留。M21/M22/M29 从真实未完成计划检查点分叉，以免绕过已完成节点不可改写规则。M30 经现有精确审批 API 同意确切本地 fixture 动作，固定模拟器只抛出未知结果、没有外部客户端；保留真实 CallIntent/未知结果，不假装已有外部收据，也不实际付款。若公开入口先拒绝某输入，记录输入拒绝及原因，不能伪造出一条运行轨迹或将其静默换成更易通过的例子。

准备 v1 发现两点，正式运行尚未开启：M01 的无冲突补读暴露状态固定优先 ours 的 occurrence 选择问题，保留失败并修正产品；M30 原先创建待审批意图后取消，取消正确关闭待办、未产生外部调用，所以不能作为“未知付款”阻断样例。M30 构造改为上述精确审批后的本地未知结果，不放宽阻断预期；原始失败仍保留，正式冻结同时绑定修订后的构造器。

## 方法与记录

三个固定方法为 `semantic`（现有完整语义预览/提案/硬验证）、`artifact_only`（现有有限产物三方规则，不检查计划/约束/效果）、`choose_ours`（完整选择 ours 状态/双文件，不做三方整合）。三者使用同一份冻结三方输入，合并阶段不调用模型/工具，不用付费或联网 LLM 基线。后两者只生成隔离候选，不绕过正式批准或写入无效历史。直接选一侧丢失另一侧增量记为不符合完整预期；不能仅因研究报告仍通过就记整合成功。

每例记录准备与方法的实际调用/字节/费用、三方差异、冲突种类/路径、Schema 拒绝、候选是否可用、是否符合冻结预期及原始证据引用。正式评估报告同时给出冲突召回、错误接纳、约束/效果违规、无冲突正确整合及审阅动作数，分母固定包含全部 30 例。输入拒绝单列，不冒充某个冲突类型的成功检测；错误或缺失结果保留为未完成。

完整 `semantic` 的无冲突例还须实际完成验证→票据→批准、核对双父和 HEAD CAS，再创建零基线新 Run 验收。基线只比较候选正确性；其任务完成率标未测，不能用主方法的实际执行填充基线结果。准备调用费用与方法成本分列；报告会明确该比较的有限范围，不声称胜过任意 LLM 合并。

先完成构造器和正常控制，再保存完整产品/锁/迁移/资产/实际驱动快照并开启正式运行。准备原型保留独立目录，不混入最终分数；正式运行期间不得修改上述字节。若产品缺陷迫使修改，保留原结果并新建版本/运行批次，不能回填旧成绩。原始字节离线独立重审和篡改拒绝测试完成后再汇总，最后与桌面/新包一起核对 S11-T01–T06；本协议本身不表示 S11 已验收。
