# S9 有界修复搜索方案

依据设计文档 5B.4、实施方案 S9 和第 6.2 节。用户已允许暂缓独立 Windows 用户环境及 S8 人工标签审阅，继续工程实现；这些项目保留待补。S8 当前保留集注入点 Top-3 为 4/8，未达 6/8，本阶段默认明确使用 `full_candidates_fallback`，不声称已经证明定位优势，也不读取评估 gold 或已见保留集来选择补丁。

## 完整交付顺序

1. 冻结沿用 S7 的类型化干预、有限模板、同一起点前置条件、有序组合身份和多维分阶段预算。
2. 建立独立的持久搜索编排、提案及试验表。提案去重与 trial 身份分离；原子保存准入、完整预算预留和任务意图。重用既有独立研究 Job/Run，不能用进程内线程或临时列表代替耐久任务。
3. 先通过 Recorded 核验已选恢复链；不向 Recorded 注入补丁，不以历史答案代表修复成功。筛选在独立 Live 或 exact 只读 Hybrid 条件下执行，复用 S7 发布校验及固定验收器。未知副作用先核对；取消后不扩展新候选。
4. 接入 `POST/GET /repair-searches`、取消入口及 CLI，展示冻结空间、顺序、候选来源、各阶段预算、已有 trial、未知与停止原因。仅完整穷尽声明空间且全部得到确定失败时，允许称“声明空间内无解”；预算不足、未完成和未知分别保留。
5. 完成 S9-T01–T07：真实单点/联合效果、恶意补丁零执行、去重、预算、无解范围和中断/重启/取消。状态最多 `screened/needs_confirmation`，不会写生产配置、宣称 verified 或 1-minimal。
6. S10 另行完成逐项删除、最终候选锁定、独立确认/回归、四种同预算基线、30 例及 20/10 划分、Repair Lab。然后继续必选 S11 和 S12-A/B/C/D；不能以本阶段或首个增量替代完整目标。

## 第一增量：纯空间与预算契约

`core/repair.py`、`repair/templates.py`、`repair/space.py`、`repair/budget.py` 不启动模型、工具或 Job，也不发布干预。模板生成只读实际 CAS 快照；所有持久干预仍由既有 S7 校验项目/事件/调用归属、录制完整性、输入、测试 split 及权限，再保存不可变定义。

固定目录 `bounded-templates/v1`：

| 模板 | 唯一修改范围 | 适用边界 |
|---|---|---|
| `prompt-verified-sources/v1` | 在 `agent_config.prompt` 后增加固定的来源、有效时间和不执行资料指令约束 | 相同模型决策前 checkpoint；既有规则不重复追加；超 16,000 字符明确不适用 |
| `prompt-required-artifacts/v1` | 增加固定的 report.md / sources.json 一致性与产物完成约束 | 不改变固定验收器、权限、模型、价格表或输入 |
| `plan-required-artifacts/v1` | 仅插入缺失的 write_report / write_sources 节点和前置依赖 | 保留全部原节点，包括已完成节点；名称冲突确定性分配；超过 64 节点明确不适用；无既有计划时不发明计划 |
| `recorded-observation/v1` | 引用显式提供、去重且最多八项的录制候选 | 仅 corpus_search / source_read，始终 test_only；不生成观测内容，S7 还须核验同签名、同参数、同 split、完整只读录制 |

模型模板先核对完整 StateSnapshot 和 AgentConfig 摘要，再复用 `prepare_live` 的工作区、预算、工具权限、已完成节点及安全起点检查。待核对、待审批、中断状态和已接受的 pending tool 不被模板清除。模板只表达待检验假设；固定 Prompt 不保证改变 Mock 行为，产物模板也不保证能修复错误资料或缺失证据。

`freeze_space` 按显式输入顺序保留前八项不同效果；相同解释或模板名不制造不同效果身份。被上限排除的补丁摘要完整列出；最多接收 1,032 个输入并归档 1,024 项排除摘要，超限拒绝，不能假称穷尽完整来源列表。声明空间只包含选入项及深度，不把排除项纳入“无解”范围。

先产生全部单点，再产生可兼容的有序双点；默认最多八原子、深度二，理论最多 64 项。两个 Prompt、两个 Plan 或同一工具 occurrence 的二次替换冲突，拒绝组合，不以后项覆盖前项。全部原子必须有相同来源、base、冻结验收器和起点 state/config。单点失败不阻断双点枚举；`[Prompt, Plan]` 与 `[Plan, Prompt]` 分别保留。

效果摘要包含目标事件/checkpoint、payload、precondition 和 effect policy，不含解释文字；提案键再绑定项目、failed Run、base、environment、validator、策略版本及有序效果摘要。独立 trial 键包含 search ID、proposal、phase 和 repeat，重复确认不会被提案去重吞掉。模板名称不构成安全凭据，外部提交不得凭名称绕过实际 S7 发布校验。

## 预算与下一增量的台账约束

默认总 30 trial，screen/reduce/confirm/regression 为 14/6/6/4；单 trial 为 6 次模型、12 次工具、4,000 Token/Mock 计量单位、60 秒；总 Token 60,000、总墙钟 900 秒、默认并发一，允许一至四。总模型/工具上限初值为 30 倍单试验上限，即 180/360。默认费用明确为零；非零费用必须冻结 USD 微单位总额、单 trial 上限和价格表版本，不能用 null 表示无限费用。现有 Mock 使用 UTF-8 字节计量，不冒充供应商 Token；真实模型需按 S7 计量保守结算。

准入同时检查阶段次数、总次数、并发、模型/工具调用、Token、费用和墙钟。已结算量加上所有未决试验的完整上限、下一 trial 上限及确认/回归预留必须不超过上限。screen 和 reduce 均保护 10 trial 的完整资源，confirm 保护 4 个回归 trial；reduce 六次是次数上限，和 screen 分享探索资源余额，不保证次数全部可用。默认确认/回归保护 40,000 Token、600 秒，探索最多使用其余 20,000 Token 和可用时间。

当前准入函数只处理可信台账快照；后续持久实现必须在领取事务内复核并保存预留，不能先检查后异步扣款。总墙钟从数据库持久开始时间计算，包含排队、重启和等待；在途试验额外保留完整时长是保守规则，允许提前停止，不允许超支后补账。未知计量保持完整预留，不能写零后释放；实际量明确时才能释放差额。基线重跑、失败、取消、超时同样占用已经启动的 trial。

后续预检必须说明预算能否覆盖最小确认/回归；不足只能产出未确认候选。首增量当时尚未实现持久台账、Recorded 预检、搜索执行、停止原因报告、API/CLI、重启或 S10 确认；不能将该增量当作 S9-T01–T07 整体通过。持久层的后续进展见下节。

## 持久意图与控制租约增量

新迁移 `0017_repair_search_ledger` 从冻结的 S8 元数据增加七张表：`repair_searches` 保存搜索条件、请求身份与失败终态，`repair_jobs` 保存可领取的编排租约/取消状态，`repair_proposals` 保存全部有序提案，`repair_trials` 保存不可变试验意图，`repair_trial_jobs` 预留真实 Job/Run 归属，`repair_trial_results` 保存不可变结算，`repair_events` 保存按任务 revision 递增的审计。历史迁移及执行表不改写；只能在独立测试库回退。

搜索发布接收已经经 S7 发布的有限原子干预。先在事务外核验原失败终态与硬断言、固定 screen 验收器、输入/代码/语料、base→失败终态的版本关系、环境和单试验预算；逐项重验 S7 定义/上下文，并冻结每个兼容有序提案及 exact Hybrid policy（如有）。事务内再次核对失败来源，锁定操作者/幂等键后原子发布；六路同键不产生多个搜索，异参冲突，失败回滚可原键重试。使用单连接池也不会持有发布事务再申请验证连接。编译不执行模型、工具或新增研究 Job。

领取通过 PostgreSQL 行锁和 `SKIP LOCKED`；租约 token、Worker、数据库截止时间共同限定修改权。新领取会替换旧 token，过期/释放的旧 Worker 不能再预留。代码版本不兼容时转 `needs_attention`，不强行继续旧搜索。搜索墙钟使用首次请求读取的数据库时刻，在发布时冻结，计入编译、等待、重启和后续排队。

预算预留的原子单位是 `repair_trials` 意图；它与预算准入、任务 revision 和审计在同一短事务提交。没有确定结算的每项意图都按完整单 trial 上限占用资源和并发，重试/重启读取同一键得到原意图，不能再扣一次或重建新身份。Recorded 前置意图排在第一项、占 screen 次数；数据库拒绝在 `chain_valid` 结算前插入筛选意图。这里的恢复链正确不代表原任务验收通过。

取消先冻结新增意图；未决项仍占完整预留。只有确定未绑定、也未产生对应研究 Job 的意图，才能在取消后结算为 `not_started` 并释放资源，已启动次数仍保留。实际已派发 Job 必须走下一增量的控制/核对流程，不能按零消耗释放。数据库拒绝历史改写、非法 revision、跨项目/搜索引用和无真实终态 Job 的成功结算。

代码不兼容的 `needs_attention` 搜索只允许转入操作者取消路径；取消用租约可处理未派发项和后续 Job 核对，不会获准恢复筛选或产生新意图。不能因为新代码无法执行旧任务，就禁止用户取消旧搜索。

该持久层增量提交时已建立台账及内部服务，但尚未接入 Recorded/Live/Hybrid 的原子派发、真实执行结果计量、停止原因全集、对外 API/CLI 和独立 repair-worker。后续试验通道见下节，完整有界搜索仍未交付；S9-T01–T07、S10 确认/缩减、S11 及 S12-A/B/C/D 继续保留完整范围。

## 原子派发与物理结算增量

`VersionService` 和 `ReplayService` 拆为事务外准备、同连接事务内发布：冻结请求、完整快照字节、祖先集合、不可变语料、配置、输入文件和 Replay spec，发布时复核 Fork 安全、权限、来源和代码版本。既有 Replay 入口保留请求幂等；默认 Job 请求身份不变。S9 派发在同一事务里创建 Fork、配置/任务、研究 Job/Run、冻结输入、`repair_trial_jobs` 归属和审计，失败回滚；提交丢失响应时复用原 Job，不能重建独立任务或再扣试验额度。

迁移 `0018_repair_dispatch_control` 在派发时再次锁定搜索 Job，拒绝取消、非运行状态和过期租约；历史迁移不改写。新增不可变 `repair_trial_waits` 和 waiting_reconciliation 状态，保存未决原因及当时缺失计量的观测快照。没有明确结算的试验继续按完整上限占用预算。即使还有并发空位，也不能在未决核对前扩展候选；全部未决项得到确定结算后才恢复筛选。旧的未知观测晚到时，事务内先检查已提交结果，不能把已结算搜索重新挂起。

Recorded 恢复验证沿用原始冻结配置，不改变历史语义；`execution_wall_ms` 只收紧该 Recorded Job 的实际执行期限，必须不大于配置上限，不成为通用 API 的新权限入口。恢复证明成功只记 `chain_valid`，物理模型/工具/Token/费用为零，原任务的失败逻辑状态保持。Live/Hybrid 从独立输入和预算执行；Hybrid 只可引用当前项目、精确修复提案所拥有的冻结 policy，保留 synthetic、只读选择及 test_only 标记。

`RepairTrialService` 从实际调用账本读取物理调用、Mock UTF-8 字节、供应商 Token 和冻结价格表估价，排除历史复用与 Hybrid 观测。硬验收使用固定验收器重新读取当前独立 Run；结果绑定研究 Job、初始/恢复后的当前 Run、报告和验收证据。预算/取消/安全停止保持非确定结论，未知费用不能按零结算；观察到超出预留的明确实际量时如实入账并停止继续搜索。取消只传给已派发 Job，由原 Worker 应用，未决效果不自动重发。

此增量提供真实试验通道和结算，不含自动候选选择循环、完整停止判定、对外搜索 API/CLI 或 repair-worker，仍不能宣称 S9 整体验收。通道验证使用显式测试预算，不默认把单次通过提升为稳定修复。

当前缺失产物例在晚期共同检查点，实际修复用了 3 次模型、2 次工具和约 47,109 个 Mock 字节计量单位。默认 4,000 单位不足，且默认 60,000 总额保护确认/回归后仅余 20,000。后续须按实施方案 6.2 冻结经测量的新版 Mock 预算策略并复验，不能静默扩大旧策略，也不能把本次 200,000 单 trial / 6,000,000 总单位的显式测试预算结果计为默认预算验收；这同样不代表真实供应商 Token 或账单。

## 自动搜索与公共模板入口增量

上述旧增量的缺项在本轮接通：Recorded 预检后按冻结顺序枚举全部单点与兼容有序双点；控制器从持久意图、Job 和结算继续，不自行运行 Agent。找到候选后排空在途试验，按安全、硬验收、补丁数、字节变更范围和实际成本选择已探索候选，保留未探索/排除范围。停止报告与租约、revision、取消标志在短事务内复核并封存，只有非空声明空间全部确定失败才允许称空间内无解。

`POST/GET /repair-searches`、取消、项目分页列表及 `repair-search/repair-status/repair-list/repair-cancel/repair-worker` 已实现。入口从给定共同 base 和目标事件自动生成有限模板；观测录制仍需显式选择并使用 Hybrid。S7 干预准备和发布分离，单连接池可用，六路同键仅创建一组定义和搜索。原始请求摘要保存于搜索根，提交后丢失响应的重试复用原搜索。模板不适用与上限排除项进入冻结空间，不能混入无解范围。

实施方案 6.2 已补充 `bounded-templates/mock-bytes-v2@<预算内容摘要>`：通常单 trial 12 模型、12 工具、200,000 字节，总 3,000,000 字节；逐维裁剪到来源授权，未来确认/回归保护 10 次完整资源。旧 v1 参数不改写。本轮原生产 Mock 在公共默认入口中，两个 Prompt 失败后自动找到 Plan 修复；总筛选为 7 次模型、4 次本地工具、99,753 字节，最终试验仍为 47,109 字节，没有用条件替身替代这项默认核对。

本轮 556 单元、64 真实集成通过，38 项新增，证据和具体边界见 [S9 自动搜索记录](acceptance/S9-search-loop.md)。下一步汇总 T01–T07 的逐项退出与安全拒绝证据，继续 S10 独立复测、缩减、基线评估与 Repair Lab，再推进必选 S11 和 S12-A/B/C/D。S8 人工审阅、4/8 Top-3 未达标、S6/D1 原生/环境前置及桌面分发范围仍如实保留，不提前标记 S9 整体验收或合并 main。

后续收尾已完成 [S9 本机后端退出矩阵](acceptance/S9-gates.md)：冻结全部已探索候选的排序与失败/未知结果、实际量和时延，严格核验选中项、唯一身份及合计；修正终态查询仍增长墙钟。五类恶意补丁由 HTTP 关联日志及零新 trial 计数核对。最新 569 单元 + 32 真实集成通过，旧证据保留不重复计数；进入 [S10 工程实施](S10-repair-plan.md)，不把 S9 自身功能退出当成前置补验、稳定修复或完整项目交付。
