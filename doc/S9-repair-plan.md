# S9 有界修复搜索方案

依据设计文档 5B.4、实施方案 S9 和第 6.2 节。用户已允许暂缓独立 Windows 用户环境及 S8 人工标签审阅，继续工程实现；这些项目保留待补。S8 当前保留集注入点 Top-3 为 4/8，未达 6/8，本阶段默认明确使用 `full_candidates_fallback`，不声称已经证明定位优势，也不读取评估 gold 或已见保留集来选择补丁。

## 完整交付顺序

1. 冻结沿用 S7 的类型化干预、有限模板、同一起点前置条件、有序组合身份和多维分阶段预算。
2. 建立独立的持久搜索编排、提案及试验表。提案去重与 trial 身份分离；原子保存准入、完整预算预留和任务意图。重用既有独立研究 Job/Run，不能用进程内线程或临时列表代替耐久任务。
3. 先通过 Recorded 核验已选恢复链；不向 Recorded 注入补丁，不以历史答案代表修复成功。筛选在独立 Live 或 exact 只读 Hybrid 条件下执行，复用 S7 发布校验及固定验收器。未知副作用先核对；取消后不扩展新候选。
4. 接入 `POST/GET /repair-searches`、取消入口及 CLI，展示冻结空间、顺序、候选来源、各阶段预算、已有 trial、未知与停止原因。仅完整穷尽声明空间且全部得到确定失败时，允许称“声明空间内无解”；预算不足、未完成和未知分别保留。
5. 完成 S9-T01–T07：真实单点/联合效果、恶意补丁零执行、去重、预算、无解范围和中断/重启/取消。状态最多 `screened/needs_confirmation`，不会写生产配置、宣称 verified 或 1-minimal。
6. S10 另行完成逐项删除、最终候选锁定、独立确认/回归、四种同预算基线、30 例及 20/10 划分、Repair Lab。然后继续必选 S11 和 S12-A/B/C/D；不能以本阶段或首个增量替代完整目标。

## 第一增量：纯空间与预算契约

`core/repair.py`、`repair/templates.py`、`repair/space.py`、`repair/budget.py` 不启动模型、工具或 Job，也不发布干预。模板生成只读实际 CAS 快照；所有持久干预仍由既有 S7 校验项目/事件/调用归属、录制完整性、输入、测试 split 及权限，再保存不可变定义。

固定目录 `bounded-templates/v1`：

| 模板 | 唯一修改范围 | 适用边界 |
|---|---|---|
| `prompt-verified-sources/v1` | 在 `agent_config.prompt` 后增加固定的来源、有效时间和不执行资料指令约束 | 相同模型决策前 checkpoint；既有规则不重复追加；超 16,000 字符明确不适用 |
| `prompt-required-artifacts/v1` | 增加固定的 report.md / sources.json 一致性与产物完成约束 | 不改变固定验收器、权限、模型、价格表或输入 |
| `plan-required-artifacts/v1` | 仅插入缺失的 write_report / write_sources 节点和前置依赖 | 保留全部原节点，包括已完成节点；名称冲突确定性分配；超过 64 节点明确不适用；无既有计划时不发明计划 |
| `recorded-observation/v1` | 引用显式提供、去重且最多八项的录制候选 | 仅 corpus_search / source_read，始终 test_only；不生成观测内容，S7 还须核验同签名、同参数、同 split、完整只读录制 |

模型模板先核对完整 StateSnapshot 和 AgentConfig 摘要，再复用 `prepare_live` 的工作区、预算、工具权限、已完成节点及安全起点检查。待核对、待审批、中断状态和已接受的 pending tool 不被模板清除。模板只表达待检验假设；固定 Prompt 不保证改变 Mock 行为，产物模板也不保证能修复错误资料或缺失证据。

`freeze_space` 按显式输入顺序保留前八项不同效果；相同解释或模板名不制造不同效果身份。被上限排除的补丁摘要完整列出；最多接收 1,032 个输入并归档 1,024 项排除摘要，超限拒绝，不能假称穷尽完整来源列表。声明空间只包含选入项及深度，不把排除项纳入“无解”范围。

先产生全部单点，再产生可兼容的有序双点；默认最多八原子、深度二，理论最多 64 项。两个 Prompt、两个 Plan 或同一工具 occurrence 的二次替换冲突，拒绝组合，不以后项覆盖前项。全部原子必须有相同来源、base、冻结验收器和起点 state/config。单点失败不阻断双点枚举；`[Prompt, Plan]` 与 `[Plan, Prompt]` 分别保留。

效果摘要包含目标事件/checkpoint、payload、precondition 和 effect policy，不含解释文字；提案键再绑定项目、failed Run、base、environment、validator、策略版本及有序效果摘要。独立 trial 键包含 search ID、proposal、phase 和 repeat，重复确认不会被提案去重吞掉。模板名称不构成安全凭据，外部提交不得凭名称绕过实际 S7 发布校验。

## 预算与下一增量的台账约束

默认总 30 trial，screen/reduce/confirm/regression 为 14/6/6/4；单 trial 为 6 次模型、12 次工具、4,000 Token/Mock 计量单位、60 秒；总 Token 60,000、总墙钟 900 秒、默认并发一，允许一至四。总模型/工具上限初值为 30 倍单试验上限，即 180/360。默认费用明确为零；非零费用必须冻结 USD 微单位总额、单 trial 上限和价格表版本，不能用 null 表示无限费用。现有 Mock 使用 UTF-8 字节计量，不冒充供应商 Token；真实模型需按 S7 计量保守结算。

准入同时检查阶段次数、总次数、并发、模型/工具调用、Token、费用和墙钟。已结算量加上所有未决试验的完整上限、下一 trial 上限及确认/回归预留必须不超过上限。screen 和 reduce 均保护 10 trial 的完整资源，confirm 保护 4 个回归 trial；reduce 六次是次数上限，和 screen 分享探索资源余额，不保证次数全部可用。默认确认/回归保护 40,000 Token、600 秒，探索最多使用其余 20,000 Token 和可用时间。

当前准入函数只处理可信台账快照；后续持久实现必须在领取事务内复核并保存预留，不能先检查后异步扣款。总墙钟从数据库持久开始时间计算，包含排队、重启和等待；在途试验额外保留完整时长是保守规则，允许提前停止，不允许超支后补账。未知计量保持完整预留，不能写零后释放；实际量明确时才能释放差额。基线重跑、失败、取消、超时同样占用已经启动的 trial。

后续预检必须说明预算能否覆盖最小确认/回归；不足只能产出未确认候选。当前未实现持久台账、Recorded 预检、搜索执行、停止原因报告、API/CLI、重启或 S10 确认；不能将本增量当作 S9-T01–T07 整体通过。
