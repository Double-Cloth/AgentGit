# S5 接管封存未知来源批次

本批延续 [模型核对](S5-settlement.md)，接通旧 Run 未观察调用即崩溃、新 Run 保存 `run.outcome_unknown` 的 Recorded 来源。完整 S5 汇总回归仍在进行，fake 外部写的原 Runtime 专项另行汇总。

## 实现与边界

`UnknownStopReader` 校验封存事件、原调用索引、独立归属的意图/请求、冻结签名及调用前检查点。允许的来源止于自身 Job 恢复根，不采用更早 Fork/Live 的其他 Job。当前串行 Runtime 的每次封存必须精确对应一个未决调用；缺失或多个调用明确拒绝。

`rebuild_unknown` 从原调用前状态和当前 Runtime 重新生成的模型/工具请求计算未知状态。步骤、调用次数、Token 预留和工具 attempt 只增加一次；若起点已包含未知状态，则核验其原轨迹与计量并原样保留。崩溃前没有观察轨迹的来源不补造回执或轨迹，不读取后来的确认响应，也不重发动作。原始调用属于模型时保留响应上限的 Token 预留。

后续核对继续走已实现的 `RecordedSettlement` 和原 Runtime `_settle`，结算先于取消/到期。范围仅到封存点时，即使调用后来已经确认，结果仍是历史 `outcome_unknown`；`verified=true` 表示未知状态被重算，不表示业务成功。即使后来的证据/回执对象不在库中，此范围也不需要它们。

每个范围内封存证明必须恰好消费一次。重算的快照和产物摘要仍逐检查点与原 Commit 对比；再次复合 Recorded 继续追溯并重算原封存路径。纯重算只读取已发布证明，不查询 Resolver、网络、工作区或容器。
