# S10 开发故障构造与真实正常对照

2026-10-27，分支 `codex/s10-repair`。在已冻结的三十套公开输入之上，接通二十个开发故障，使用既有 Research Runtime、Gateway、PostgreSQL 和 CAS 运行。37 项构造契约及 20 项真实集成分批通过，共 57 个不同测试节点。此记录只证明开发故障和正常对照的构造有效，没有候选搜索、修复成绩、正式保留集或 D2 结论。

## 机制与隔离

`repair_fault_runtime.py` 是评估辅助模块，不进入产品包。评估驱动依据规格编译 FaultCondition；模型只收到机制条件和实际公开 ModelRequest，不接收 case_id、split、family、declared_repairable、方法、trial 阶段、期望验收或正确补丁。响应不依靠 trial 序号或先前结果改变，同一条件及请求具有确定性。调用签名绑定条件及适配器源码摘要；原始响应逐条由独立审计重算。

开发机制包括计划遗漏产物、选择未支持事实或未读取的过期/未来副本、错误结论覆盖、按排名错误归属、序列化丢失及外部指令诱导的路径越界。过期/未来副本仅出现在错误报告的证据选择中，与真实读取的规范来源不一致，由原证据身份规则拒绝；没有给验收器添加正确答案或允许其通过。缺报告/缺来源会遮蔽其他错误，因此联合机制另外用构造工作记忆分别核对选择约束与完整计划，不把这种静态核对视为已验证联合修复。

外部指令作为原文追加到规范来源正文，并重新计算 body_sha256，再冻结同一 Goal/语料验收器。R19/R20 的公开运行输入因此与基准输入摘要不同；事实及合法任务目标保持，故障 Run 和正常对照共享同一派生规范语料。不能只改 source_read 返回却继续声称使用未变语料，不能忽略证据不一致来制造修复通过。

固定 Prompt 文本识别只是合成模型的约束遵守机制。契约核对选择缺陷可受严格证据约束影响、排名缺陷依赖真实 observation、序列化缺陷不被两条 Prompt 约束关闭。这里没有真实供应商、无偏随机或提示泛化结论，也没有有限空间无解证明；后者仍须完整搜索结果支持。

## 真实失败与正常对照

每个开发输入均创建一个故障源 Run 和一个独立生产 MockResearchModel 对照；冻结验收器在两者执行前创建，配置及三工具授权相同。最终归档为 40 个不同 Run：20 个失败、20 个正常通过。保留集 R21–R30 没有实际 Run。

最终原始记录共 434 次模型、350 次工具调用，4,224,205 Mock UTF-8 字节；单 Run 为 66,410–138,105 字节。原字节按仓库求和 14,753,199，6,524 个对象条目，不宣称跨仓去重。源构造沿用原研究配置上限，并单列准备成本；两项越界源因重规划各运行 13 次模型调用，不能把它们当作满足 12 调用单 trial 上限的修复试验，也没有扩大后续共同搜索预算。

两项越界写均保留两次底层 `validation` 拒绝，零成功 artifact_write、零产物；第三次重复决策触发现有 `loop_detected` 停止。正常对照使用同一含外部原文的规范语料，仍生成正确两份产物并通过。没有新增 Shell/Python 授权、宿主执行或越界文件清理行为。

独立审计从 CAS 类型域摘要、仓库归属和完整事件索引开始，重新读取冻结验收器、Goal/语料、最终状态、原始请求/响应；逐条验证模型签名和响应字节，重新计算硬验收及实际调用/字节计量。所有评估仍为 failed/passed 原始结论，没有用归档自述代替证据。

首次真实批次的 R01–R18 通过，R19 因测试错误预期最终停止码为 forbidden 而失败；实际零写入及循环停止均已发生。只修正测试断言，并补核底层两次拒绝，再执行 R19/R20 两项通过。原型 XML 与测试源码保留，不重复累计失败节点；首次 R19 的额外两个构造 Run 不属于最终四十项归档或任何研究成绩。早期四项纯契约错误已在运行前修正，旧报告同样不累计。
